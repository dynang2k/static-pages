개요

이 영상은 클로드 코드(Claude Code)의 새 기능인 "에이전트 팀(Agent Teams)"을 기존의 "서브 에이전트(Subagent)"와 비교하며 설명한다. 서브 에이전트는 메인 컨텍스트와 분리된 별도 컨텍스트에서 혼자 작업하고 결과 요약만 보고하는 "프리랜서" 방식인 반면, 에이전트 팀은 팀원들이 서로 메시지를 주고받고 공유 작업 목록(테스크 리스트)을 통해 협업하는 "하나의 팀" 방식이다. 강사는 팀장-팀원 간 협업이 필요 없는 업무(4개 지역 독립 보고서)와 협업이 필요한 업무(하나의 사업 기획안을 위한 시장조사·경쟁사분석·예산·일정)를 회사 비유로 대조시켜, 언제 서브 에이전트로 충분하고 언제 에이전트 팀이 필요한지를 직관적으로 보여준다. 영상 후반부에는 실제 설정 방법(settings.json에서 실험적 기능 활성화), 다섯 가지 핵심 용어(팀 리드, 팀메이트, 스폰, 테스크 리스트, 메일박스), 그리고 팀원들의 작업 화면을 보는 두 가지 표시 모드(인프로그레스 모드, 스플릿 페인즈 모드)를 실습으로 보여준다. [보강] 공식 문서(code.claude.com)를 확인한 결과 Agent Teams는 여전히 실험적(experimental) 기능이며, 활성화 환경변수는 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1이다. 세션 재개(/resume, /rewind), 팀 중첩(nested team), 리더 교체 등에 알려진 제약이 있다는 점도 문서에 명시되어 있다 (code.claude.com/docs/en/agent-teams).

주제별 상세 정리

서브 에이전트 vs 에이전트 팀 — 회사 비유로 본 차이

강사는 시청자를 "팀장" 역할로 놓고 두 가지 상황을 대조한다. 첫 번째 상황은 상사가 "4개 지역(서울, 부산, 대구, 광주)의 커피 프랜차이즈 시장 보고서"를 요청한 경우다. 각 지역 보고서는 서로 관련이 없으므로 팀원 4명에게 하나씩 맡기고 각자 독립적으로 조사해서 완성본만 받으면 끝난다. 팀원끼리 대화할 필요가 전혀 없는 이런 방식이 바로 지금까지 사용해온 "서브 에이전트" 방식이다.

두 번째 상황은 "직장인 점심 도시락 배달 서비스 런칭 기획안"을 요청받은 경우다. 마찬가지로 팀원 4명에게 시장조사, 경쟁사 분석, 예산안, 일정표를 나눠 맡기지만, 이번엔 서로 정보가 필요하다. 예를 들어 예산 담당 팀원이 예산을 짜다가 "직장인 도시락 시장 규모가 얼마나 나왔어?"라고 시장조사 담당 팀원에게 직접 물어봐야 막힘없이 업무를 진행할 수 있다. 이렇게 서로 소통하며 협업해야 하는 업무 방식이 "에이전트 팀"이다. 강사는 "같은 네 명인데 업무 성격에 따라 일하는 방식이 완전히 달라진다"는 점을 핵심 포인트로 짚는다.

[보강] 공식 문서는 이 구분을 표로 명확히 정리한다. 서브 에이전트는 "결과만 중요한 집중형 작업(focused tasks where only the result matters)"에 적합하고, 에이전트 팀은 "논의와 협업이 필요한 복잡한 작업(complex work requiring discussion and collaboration)"에 적합하다고 명시한다. 또한 서브 에이전트는 "메인 에이전트가 모든 작업을 관리(Main agent manages all work)"하는 반면 에이전트 팀은 "메시지와 공유 테스크 리스트를 통한 자기 조율(Self-coordination through messages, plus a shared task list)"이라는 점이 공식 비교표의 핵심 차이로 제시된다 (code.claude.com/docs/en/agent-teams).

에이전트 팀 실행 데모 — 도시락 배달 서비스 기획안 만들기

강사는 개념 설명에 앞서 실제 동작 화면을 먼저 보여준다("복잡한 개념은 실제로 돌아가는 모습을 먼저 보여준 뒤 설명을 들으면 훨씬 빠르게 이해된다"는 것이 본인의 강의 스타일이라고 밝힘). 클로드 코드에 "에이전트 팀을 사용해서 직장인 점심 도시락 배달 서비스 런칭 기획안을 만들어 달라, 팀원을 4명 생성하고 각각 시장조사, 경쟁사 분석, 예산안, 일정표를 담당하게 한 뒤 결과를 하나의 기획안으로 종합해 달라"고 요청하면, 팀장(팀 리드) 세션이 먼저 4개의 테스크(작업)를 생성하고 이어서 팀원 4명을 동시에 스폰(생성)한다.

우측 분할 화면에는 각 팀원이 맡은 업무를 수행하는 모습이 동시에 표시된다. 시장조사, 예산안 작성, 로드맵(일정표) 작성, 경쟁사 분석을 각각 맡은 팀원들이 병렬로 작업하는 것을 확인할 수 있다. 강사는 "AI를 어떻게 다뤄야 할지 잘 모르겠다면 이 팀장과 팀원들을 실제 사람이라고 생각해보라"고 조언하며, 진행 상황이 궁금하면 팀장에게 직접 물어보면 된다고 설명한다. 실제로 "진행 상황을 확인해 달라"고 요청하자 팀장이 "시장조사 완료, 경쟁사 분석 작업 중, 예산안 완료, 로드맵 작업 중"이라는 식으로 각 팀원의 상태를 취합해 보고한다. 시장조사를 마친 팀원은 추가 작업이 필요하면 요청해 달라며 대기 상태로 전환된다.

모든 작업이 끝나면 팀장이 "종합 기획안을 작성하고 팀을 마무리하겠다"고 알리는데, 강사는 결과를 더 살펴보기 위해 "팀을 정리하지 말라"고 요청한다. 결과물은 "런치박스 플랜"이라는 디렉터리에 저장되며, 1~4번 파일에는 각 팀원의 개별 분석 결과가, 0번 "파이널 플랜" 파일에는 팀장이 종합한 최종 기획안이 정리되어 있다. 실제로 해당 파일을 열어보면 직장인 점심 도시락 배달 서비스 론칭 기획안이 잘 작성되어 있는 것을 확인할 수 있다.

팀 리드(팀장)와 팀메이트(팀원)의 구조

화면 좌측에 보이는 세션이 팀 리드, 즉 팀장 역할을 한다. 사용자가 터미널에서 claude 명령어로 실행한 바로 그 클로드 코드 세션이 팀 리드가 되며, 이 세션에 "에이전트 팀을 생성해 달라"고 요청하면 해당 세션이 팀장이 되어 작업을 나누고 팀원을 생성(스폰)한 뒤, 각 팀원의 결과를 종합해서 사용자에게 응답한다.

화면 우측의 분할 화면들은 팀메이트, 즉 팀원들이다. 팀 리드가 필요에 따라 추가로 만든 각각의 독립된 클로드 코드 세션이다. 핵심은 각 팀원이 완전히 독립된 클로드 코드 세션으로 실행된다는 점이며, 이 때문에 팀 리드에게 프롬프트를 입력하듯 각 팀원에게도 직접 프롬프트를 요청할 수 있다. 또한 팀원이 업무를 마치고 팀 리드에게 보고를 끝낸 상태여도, 팀원이 조사했던 대화 이력은 그대로 남아있다. 팀원들은 서브 에이전트와 달리 메시지를 서로 주고받을 수 있고, "테스크 리스트"라는 작업 목록을 공유함으로써 함께 협업해 나간다.

강사는 급한 경우 팀장을 거치지 않고 팀원에게 직접 요청할 수 있다는 점을 실습으로 보여준다. 시장조사 담당 팀원에게 "안녕"이라고 인사하자 "안녕하세요, 무엇을 도와드릴까요?"라고 응답하고, 경쟁사 분석 담당 팀원에게도 인사를 요청하자 팀원들끼리 서로 메시지를 주고받으며 인사를 나누고, 나아가 핵심 협업 전략에 대해서도 서로 대화를 나눈다(경쟁사 분석 담당 팀원도 이 협업 방식에 동의했다고 응답). 팀 리드 세션을 다시 확인해보면, 팀원들끼리 인사를 주고받으며 협업을 논의했던 내용을 팀장이 관찰하고 있는 것도 확인할 수 있다.

[보강] 공식 문서에 따르면 팀원 간 메시지는 SendMessage 도구를 통해 전달되며, 각 에이전트의 메일박스는 ~/.claude/teams/{team-name}/inboxes/{agent-name}.json 경로의 JSON 파일로 구현되어 있다. 메시지 전달은 파일 쓰기가 성공했을 때만 "전송됨"으로 처리되며, 디스크가 꽉 차거나 메일박스 디렉터리에 쓰기 권한이 없는 경우 발신 에이전트가 오류를 받는다. 또한 팀원이 다른 에이전트로부터 받은 메시지는 "사용자가 아닌 다른 클로드 세션에서 온 메시지"로 명시적으로 처리되어, 권한 프롬프트를 팀원이 대신 승인하거나 거부된 작업을 다른 팀원에게 우회시키는 것이 원천적으로 차단된다 (code.claude.com/docs/en/agent-teams).

서브 에이전트의 세 가지 한계

강사는 서브 에이전트의 동작 원리부터 정리한다. 서브 에이전트는 메인 컨텍스트와 분리된 별도의 컨텍스트를 가진 에이전트로, 메인 컨텍스트에서 대화를 하다가 서브 에이전트를 호출하면 서브 에이전트가 자기만의 컨텍스트 안에서 작업을 수행하고, 작업이 끝나면 결과만 요약해서 메인 컨텍스트로 돌려준다. 이 방식의 장점은 서브 에이전트가 파일 100개를 뒤져도 메인 컨텍스트는 깨끗하게 유지된다는 점이다 — 결과 요약 몇 줄만 넘어오기 때문에 메인 컨텍스트가 금방 차버리는 문제를 막아주고, 더 길고 복잡한 작업을 이어갈 수 있게 해준다.

하지만 이런 서브 에이전트에는 세 가지 분명한 한계가 있다. 첫째, 서브 에이전트를 병렬로 여러 개 실행했을 때 서브 에이전트끼리 직접 대화를 못 한다. 강사는 이를 "프론트엔드 개발자 A가 API 스펙 문제를 발견했는데 바로 옆에 앉은 백엔드 개발자 B에게 직접 말을 못 하는 상황"에 비유한다. 둘째, 결과 요약만 메인 컨텍스트로 돌아오기 때문에 중간에 발견된 미묘한 단서들이 사라진다. 예를 들어 서브 에이전트가 파일 50개를 분석하면서 "이 파일에서 이상한 패턴을 발견했는데 당장은 문제가 아니네"라고 넘어간 부분이 있어도, 메인 컨텍스트에는 최종 요약 몇 줄만 돌아오므로 나중에 "아까 그 파일에서 뭘 봤었지?"라고 물어볼 수 없다. 셋째, 메인 에이전트(팀장) 혼자서 모든 서브 에이전트를 관리해야 한다. 서브 에이전트가 늘어날수록 메인의 부담이 커지고 병목이 생기며, 이러한 조율 작업으로 메인 컨텍스트가 빠르게 차버리면 더 복잡한 작업을 이어가기 어려워진다.

강사는 이를 정리하며, 서브 에이전트가 서로 소통이 필요 없는 2~3개 작업일 때는 괜찮지만, 작업이 복잡해져서 서브 에이전트를 여러 개 돌리다 보면 메인 컨텍스트가 조율하느라 빠르게 차버리거나 서브 에이전트끼리 정보를 공유해야 하는 상황이 생기며, 클로드 코드 공식 문서에서도 바로 이 시점을 "에이전트 팀으로 넘어갈 타이밍"이라고 콕 집어 말한다고 설명한다. 아이디어는 단순하다 — 팀장이 모든 걸 중계하지 말고, 팀원끼리 직접 소통하고 스스로 작업을 나눠 가지게 하자는 것.

[보강] 실제 공식 문서는 오히려 반대 순서의 조언도 함께 제시한다: "팀을 구성하기 전에 더 가벼운 대안이 충분한지 먼저 확인하라(Before you set up a team, check whether a lighter option does the job)"며, 단일 세션 내에서 동작하는 서브 에이전트나, 사용자가 직접 실행하는 세션들 사이에 메시지를 전달하는 "크로스 세션 메시징(cross-session messaging)" 기능을 먼저 검토할 것을 권한다. 즉 에이전트 팀은 "항상 더 나은 선택"이 아니라 "조율 오버헤드와 토큰 비용이 정당화될 때만" 쓰는 무거운 도구로 자리매김되어 있다 (code.claude.com/docs/en/agent-teams).

서브 에이전트와 에이전트 팀의 네 가지 차이 (공식 문서 기준)

공식 문서를 기준으로 강사는 네 가지 관점에서 두 방식을 대조한다.

① 컨텍스트 관점: 서브 에이전트는 작업이 끝나면 결과 요약만 메인에게 돌아온다. 예를 들어 서브 에이전트에게 프로젝트 파일 전체를 분석하라고 시켰을 때, 파일 50개를 뒤지다가 "이 파일은 조금 수상한데 일단 넘어가자"라고 지나친 것이 있어도 메인에게는 최종 요약 몇 줄만 돌아오고, 중간에 스쳐 지나간 단서는 사라진다. 반면 에이전트 팀의 팀원은 완전히 독립된 자기만의 컨텍스트를 유지하기 때문에, 그 수상한 파일 정보도 팀원의 컨텍스트에 그대로 남아있어서 나중에 "아까 그 파일 다시 봐봐"라고 요청할 수 있다.

② 소통: 서브 에이전트는 메인에게만 보고한다. 예를 들어 보안 담당 서브 에이전트가 코드를 보다가 "이 부분이 성능에도 영향을 줄 수 있겠는데"라고 느껴도, 성능을 담당하는 서브 에이전트에게 직접 말을 못 한다. 전달하려면 메인에게 보고하고 메인이 다시 전달해야 하는 구조다. 반면 에이전트 팀에서는 보안 담당 팀원이 성능 담당 팀원에게 바로 "이거 한번 봐봐"라고 메시지를 보낼 수 있어 더 효과적으로 업무를 처리할 수 있다.

③ 조율: 서브 에이전트는 메인이 전부 관리한다 — "A야 이거 해, B야 저거 해, 끝나면 다음 이거 해" 식으로 서브 에이전트의 작업을 매번 지시해야 한다. 반면 에이전트 팀은 공유된 테스크 리스트가 있어서, 리드가 작업을 할당하기도 하고 팀원이 자기 작업이 끝나면 다음 테스크를 스스로 가져가기도 한다. 매번 팀장이 지시하지 않아도 공유된 작업 목록을 활용해 효율적으로 일할 수 있다.

[보강] 공식 문서는 테스크에 "의존성(dependencies)" 개념이 있다고 설명한다. 특정 작업이 완료되지 않으면 그 작업에 의존하는 다른 작업은 아직 대기(pending) 상태이더라도 팀원이 가져갈 수 없으며, 의존하던 작업이 완료되면 클로드 코드가 자동으로 후속 작업의 잠금을 해제한다. 또한 여러 팀원이 동시에 같은 작업을 가져가려는 경쟁 상태(race condition)를 막기 위해 "파일 잠금(file locking)" 방식으로 작업 선점을 처리한다는 세부 구현도 명시되어 있다 (code.claude.com/docs/en/agent-teams).

④ 비용: 에이전트 팀이 서브 에이전트보다 비용이 높다. 서브 에이전트는 별도의 컨텍스트를 갖고 작업이 끝나면 사라지지만, 에이전트 팀은 각자 독립된 클로드 세션을 계속 유지하며 사용한다. 팀원이 세 명이면 대략 세 배 이상의 토큰이 사용된다고 보면 된다. 강사는 이를 한 줄로 요약한다 — "서브 에이전트는 시키면 혼자 다 하고 결과만 보고하는 프리랜서라면, 에이전트 팀은 서로 대화하면서 같이 일하는 하나의 팀이다."

[보강] 실전 가이드(Builder.io)는 실측치로 "에이전트 팀은 단일 세션 대비 대략 3~4배의 토큰을 소비한다(3–4x the tokens of a single session)"고 밝히며, 영상에서 언급한 "세 명이면 세 배 이상"이라는 설명과 대체로 일치한다. 또한 공식 문서는 인프로세스(in-process) 팀원의 요청이 메인 대화의 프롬프트 캐시 TTL 버킷 밖에서 처리되어 기본적으로 캐시가 5분만 유지되며(구독제 요금제 포함), 1시간으로 유지하려면 subagentPromptCacheTtl 설정을 1h로 지정해야 한다고 안내한다 — 다만 API에서는 1시간 캐시 쓰기에 더 높은 요금이 적용된다 (code.claude.com/docs/en/agent-teams).

에이전트 팀의 다섯 가지 핵심 용어

강사는 회사 조직도에 비유해 다섯 가지 핵심 용어를 설명한다.

  • 팀 리드(Team Lead): 팀을 만든 클로드 코드 세션 자체가 팀 리드가 된다. 사용자는 사장님이고, 사장님의 지시를 받는 팀장이 팀 리드다. 한 번 리드가 정해지면 변경할 수 없다.
  • 팀메이트(Teammate): 팀원. 리드가 만든 클로드 코드의 추가 세션이며, 각 팀메이트는 자기 자신만의 독립된 컨텍스트를 가지고 그 안에서 작업한다.
  • 스폰(Spawn): 새로운 팀원 세션을 생성하는 것. 게임에서 캐릭터가 생성되는 것처럼, 리드에게 "팀원 세 명을 만들어 줘"라고 요청하면 리드가 팀원을 스폰한다.
  • 테스크 리스트(Task List): 모든 팀원이 함께 보는 공유 작업 목록. 리드가 작업 목록을 만들면 팀원들이 이를 하나씩 처리하는 구조다. 각 작업에는 대기 중 → 진행 중 → 완료됨의 세 단계 상태가 있다. 작업을 가져가는 방식은 두 가지다: (1) 리드가 직접 지정하는 방식 — "시장조사는 A, 경쟁사 분석은 B, 예산은 C" 식으로 배정하며, 한 팀원에게 여러 작업을 미리 배정할 수도 있다(예: "시장조사와 고객 설문 분석은 둘 다 A가 해"라고 하면 A가 시장조사를 마치자마자 바로 다음 작업으로 넘어감). (2) 팀원이 스스로 가져가는 방식 — 자기 작업이 끝났는데 테스크 리스트에 아무한테도 배정되지 않은 작업이 남아있으면 팀원이 알아서 가져간다. 이는 팀장의 부담을 줄이면서 효율적으로 업무를 처리할 수 있게 해준다.
  • 메일박스(Mailbox): 팀원끼리 메시지를 보내는 시스템. 이 시스템 덕분에 리드와 팀원 사이, 팀원과 팀원 사이에 모두 메시지를 주고받을 수 있다.

[보강] 공식 문서 기준으로 팀/작업 데이터는 세션 ID 기반 이름(session- + 세션 ID 앞 8자리)으로 로컬에 저장된다. 팀 설정 파일은 ~/.claude/teams/{team-name}/config.json이고 테스크 리스트는 ~/.claude/tasks/{team-name}/에 저장되며, 세션이 종료되면 팀 설정 디렉터리는 자동 삭제되지만 테스크 리스트 디렉터리는 로컬에 남아 세션을 재개했을 때도 작업 기록을 유지한다(업로드는 되지 않음). 다만 인프로세스(in-process) 방식으로 스폰한 팀원 자체는 /resume이나 /rewind로 복원되지 않는다는 제약이 문서에 명시되어 있다 (code.claude.com/docs/en/agent-teams).

실습: 에이전트 팀 활성화 및 실행

에이전트 팀은 아직 실험적(experimental) 단계이기 때문에 기본적으로 비활성화되어 있다. 활성화하려면 settings.json 파일에 해당 환경 변수를 1로 설정해야 한다. 강사는 실제로 설정 파일을 열어 환경 변수를 1로 바꾼 뒤 바로 실습을 진행한다.

[보강] 공식 문서에 명시된 정확한 설정값은 다음과 같다:

{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}

이 값을 켜면 부수 효과도 있다는 점이 문서에 강조되어 있는데, 클로드가 스스로 이름을 붙여 실행하는 일반 서브 에이전트도 에이전트 팀 기능이 켜져 있으면 자동으로 "팀원(teammate)"으로 승격되어 실행된다. 즉 사용자가 명시적으로 팀을 요청하지 않아도 팀이 형성될 수 있다는 뜻이다. 이 동작을 원치 않으면 환경 변수를 다시 0으로 설정하면 되며, 세션을 새로 시작할 필요 없이 설정 파일 저장 시 즉시 반영된다. 또한 비대화형 모드(-p 플래그, Agent SDK 세션 포함)에서는 에이전트 팀이 활성화되어 있어도 팀원을 스폰하지 않고 일반 서브에이전트로만 동작한다 (code.claude.com/docs/en/agent-teams).

활성화 후에는 클로드에게 자연어로 팀 구성을 요청하면 된다. 강사는 넥스트(Next.js)로 관리되는 프로젝트에서 "세 명의 팀원을 만들어서 각각 보안, 성능, 스타일을 리뷰해 달라"고 자연스럽게 요청한다. 요청 즉시 팀이 생성되고 테스크 리스트가 작성되며, 테스크 소유자가 배정되고 팀원들이 동시에 스폰(생성)된다.

팀원들이 각각 어떤 작업을 하고 있는지 확인하는 방법도 시연한다. Shift + 방향키 아래를 누르면 현재 팀 리드와 그 아래 세 명의 팀원 목록이 표시된다. "스타일 리뷰" 팀원에서 엔터를 누르면 해당 팀원의 세션(하나의 독립된 클로드 코드 세션)으로 진입해 실제로 스타일을 리뷰·검토하는 과정을 볼 수 있다. 같은 방식으로 "시큐리티 리뷰어" 팀원을 확인하면, 이미 보안 리뷰를 완료하고 테스크 1번을 "완료(Complete)" 상태로 업데이트했으며 결과 보고서를 팀 리드에게 전송했다는 것을 알 수 있다. 다시 팀 리드 세션으로 돌아가 "지금 상황을 보고해"라고 요청하면, 전체 테스크가 이미 완료되었고 팀원들도 모두 대기(idle) 상태라는 종합 보고를 받을 수 있다 — 각 팀원은 리뷰를 완료한 뒤 추가 작업이 있으면 대기하는 방식으로 동작한다.

두 가지 디스플레이 모드: 인프로그레스 모드와 스플릿 페인즈 모드

에이전트 팀을 실행할 때 팀원들의 작업을 어떻게 보여줄지 두 가지 표시 모드가 있다.

인프로그레스(In Progress) 모드는 기본 모드로, 하나의 터미널에서 Shift + 방향키 아래를 이용해 팀원들을 순환하며 보는 방식이다. 모든 터미널에서 동작하고 추가 설치가 필요 없다. 앞서 실습에서 사용한 방식이 바로 이 모드다. Shift + 방향키 아래로 팀원을 선택하고 엔터로 해당 세션에 진입하며, 다시 Shift + 방향키 아래 후 "하이드(Hide)"를 선택하면 숨기고 다른 팀원으로 전환할 수 있다.

스플릿 페인즈(Split Panes) 모드, 즉 분할 창 모드는 화면을 분할해서 각 팀원을 동시에 볼 수 있는 표시 모드다(영상 초반 도시락 배달 서비스 데모에서 사용된 우측 분할 화면이 이 모드). 이 모드를 사용하려면 tmux(티웍스) 또는 iTerm2 터미널이 필요하다. tmux는 터미널 멀티플렉서(terminal multiplexer)의 약어로, 하나의 터미널 화면을 여러 개로 나눠주는 도구이며 macOS와 리눅스 환경에서 사용 가능하고 윈도우에서는 WSL 환경을 통해 사용할 수 있다. iTerm2는 macOS 전용 터미널 앱으로, macOS 기본 터미널보다 더 고급 기능을 제공하는 터미널이다. 이 도구들은 macOS나 리눅스 기반에서만 실행되므로, 윈도우 사용자는 인프로그레스 모드로 Shift + 방향키를 이용해 팀원 세션을 확인하는 방식을 사용하면 된다. 화면을 나눠서 동시에 보지 못할 뿐 기능은 동일하다.

이러한 디스플레이 모드는 설정에서 "팀메이트 모드(teammate mode)"로 지정할 수 있으며, 설정값으로는 auto, in-progress, 분할 창 모드를 쓸 때는 tmux를 지정하면 된다. auto로 설정하면 tmux 또는 iTerm2 환경에서는 분할 창 모드가 자동 선택되고, 그 외 환경에서는 인프로그레스 모드가 자동 선택된다.

[보강] 이 부분은 클로드 코드 버전에 따라 동작이 달라진 부분이라 최신 공식 문서 기준으로 보완이 필요하다. v2.1.179 이전에는 기본값이 "auto"였지만, 이후 버전부터는 기본값이 "in-process"로 변경되었다 — 즉 영상 제작 시점(구버전)에는 tmux/iTerm2 환경에서 자동으로 분할 창이 열렸지만, 최신 버전에서는 명시적으로 teammateMode를 "auto"나 "tmux"로 설정하지 않으면 항상 인프로세스 모드로 시작한다. 설정 방법은 ~/.claude/settings.json에 다음과 같이 지정한다:

{
  "teammateMode": "auto"
}

또는 세션 단위로 claude --teammate-mode auto 플래그를 사용할 수 있다(실험적 기능이라 claude --help에는 표시되지 않음). 또한 v2.1.186부터는 "iterm2" 값으로 iTerm2 네이티브 분할 창을 명시적으로 지정할 수 있으며, 이 경우 it2 CLI 설치가 필요하다. 문서는 분할 창 모드가 VS Code 통합 터미널, Windows Terminal, Ghostty에서는 지원되지 않는다고 명확히 밝히고 있어, 이런 터미널을 쓰는 사용자는 반드시 인프로그레스 모드를 사용해야 한다 (code.claude.com/docs/en/agent-teams).

[보강] 팀 규모와 운영에 대한 공식 권장 사항

영상에서 다루지 않은 실전 운영 가이드를 공식 문서와 실전 후기에서 보충한다. 공식 문서는 팀 크기에 대해 "하드 리밋은 없지만 대부분의 워크플로우에서는 3~5명의 팀원으로 시작하라"고 권장하며, "독립적으로 작업 가능한 15개 작업이 있다면 팀원 3명이 좋은 출발점"이라는 구체적 기준도 제시한다. 팀원이 늘어날수록 토큰 비용은 선형적으로 증가하고, 조율 오버헤드도 늘어나며, 일정 규모를 넘어서면 팀원을 늘려도 속도 향상이 비례하지 않는 "수확 체감(diminishing returns)"이 발생한다고 설명한다. 실전 가이드(Builder.io)도 "3~5명의 팀원이 실질적 한계치이며 그 이상은 조율 오버헤드가 이점을 상쇄한다"고 동일하게 조언한다 (code.claude.com/docs/en/agent-teams, Builder.io: You Probably Don't Need Claude Agent Teams).

작업(task) 크기 조절에 대해서도 문서는 "너무 작으면 조율 오버헤드가 이득을 초과하고, 너무 크면 체크인 없이 오래 작업해서 낭비 위험이 커진다"며, 함수 하나, 테스트 파일 하나, 리뷰 하나처럼 "명확한 산출물을 내는 자기완결적 단위"가 적절하다고 권장한다. 또한 두 팀원이 같은 파일을 동시에 편집하면 덮어쓰기 충돌이 발생하므로, 팀원마다 서로 다른 파일 집합을 담당하도록 작업을 나눠야 한다고 강조한다. 공식 문서가 제시하는 대표 활용 사례는 (1) PR을 보안·성능·테스트 커버리지 세 가지 관점에서 동시에 리뷰하는 "병렬 코드 리뷰"와, (2) 원인이 불분명한 버그에 대해 여러 팀원이 서로 다른 가설을 세우고 서로의 이론을 반박하며 토론하게 하는 "경쟁 가설 디버깅"이다. 후자는 한 명의 에이전트가 순차적으로 조사하면 첫 번째로 발견한 그럴듯한 원인에 "고착(anchoring)"되기 쉬운 반면, 여러 팀원이 독립적으로 서로의 이론을 반박하면 실제 근본 원인이 생존할 가능성이 높아진다는 논리로 설명된다 (code.claude.com/docs/en/agent-teams).

핵심 키워드/용어

  • 서브 에이전트(Subagent): 메인 컨텍스트와 분리된 별도 컨텍스트에서 독립적으로 작업하고, 완료 후 결과 요약만 메인 컨텍스트에 반환하는 기존 방식. 서브 에이전트끼리는 직접 소통할 수 없다.
  • 에이전트 팀(Agent Teams): 팀 리드와 여러 팀메이트(팀원)가 각자 독립된 클로드 코드 세션을 유지하면서, 서로 메시지를 주고받고 공유 테스크 리스트를 통해 협업하는 새로운 방식. 실험적 기능으로 기본 비활성화 상태이며, 환경 변수 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1로 활성화한다 [보강: 정확한 변수명].
  • 팀 리드(Team Lead): 팀을 생성한 클로드 코드 세션. 회사 비유에서 "팀장" 역할이며, 한 번 지정되면 변경 불가.
  • 팀메이트(Teammate): 팀 리드가 스폰한 팀원 세션. 독립된 컨텍스트를 가짐.
  • 스폰(Spawn): 팀 리드가 새로운 팀원 세션을 생성하는 행위.
  • 테스크 리스트(Task List): 모든 팀원이 공유하는 작업 목록. 각 작업은 대기 중 → 진행 중 → 완료됨 상태를 가지며, 리드가 배정하거나 팀원이 스스로 가져갈 수 있다. [보강] 작업 간 의존성(dependency)이 있을 수 있으며, 선행 작업이 완료되어야 후행 작업의 잠금이 자동 해제된다.
  • 메일박스(Mailbox): 팀 리드-팀원, 팀원-팀원 간 메시지를 주고받는 시스템. [보강] 실제로는 ~/.claude/teams/{team-name}/inboxes/{agent-name}.json 경로의 JSON 파일로 구현된다.
  • 인프로그레스 모드(In Progress Mode): 하나의 터미널에서 Shift+방향키로 팀원 세션을 순환하며 보는 디스플레이 모드. 모든 터미널에서 동작하며, [보강] 최신 버전 기준 기본값이다.
  • 스플릿 페인즈 모드(Split Panes Mode): 화면을 분할해 모든 팀원을 동시에 보는 디스플레이 모드. tmux 또는 iTerm2 필요. [보강] VS Code 통합 터미널, Windows Terminal, Ghostty에서는 지원되지 않는다.
  • tmux(티웍스): 터미널 멀티플렉서. 하나의 터미널 화면을 여러 개로 분할해주는 도구. macOS/Linux 지원, Windows는 WSL 통해 사용 가능.
  • iTerm2(아이템 2): macOS 전용 고급 터미널 앱. [보강] 분할 창 모드에서 iTerm2를 쓰려면 it2 CLI 설치와 iTerm2의 Python API 활성화가 필요하다.
  • [보강] 크로스 세션 메시징(Cross-session messaging): 에이전트 팀을 만들지 않고도, 사용자가 직접 실행한 여러 클로드 코드 세션 사이에 메시지를 전달하는 더 가벼운 대안. 공식 문서는 팀을 구성하기 전에 이 옵션이 충분한지 먼저 검토하라고 권장한다.
  • [보강] Git 워크트리(Git worktrees): 자동화된 팀 조율 없이 사용자가 직접 여러 클로드 코드 세션을 수동으로 병렬 실행하는 또 다른 대안.

언급된 링크·자료

  • 영상 내 언급: 클로드 코드 강의(인프런) 및 업데이트 기념 이벤트 링크는 원본 영상의 고정 댓글에 있다고 언급됨(URL 직접 노출 없음).
  • 클로드 코드 공식 문서: 에이전트 팀으로 전환할 타이밍에 대한 언급 있음(영상에서 구체적 URL 미제공).
